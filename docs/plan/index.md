# Что осталось сделать

Список открытых вопросов проекта: то, что нельзя было ни вывести из документации, ни
проверить на машине разработки. Каждый пункт - с обоснованием, чтобы следующий читатель
не начинал с нуля.

## T001 - opt-level релизной сборки: измерено, решение принято

Измерено в контейнере (`linux/amd64` под эмуляцией на Apple Silicon), тулчейн 1.92.0,
библиотеки обеих целевых платформ, `cargo build --release`:

| сборка | Linux `.so` | Windows `.dll` |
| --- | --- | --- |
| `opt-level=z`, стабильная | 963 856 | 3 850 240 |
| `opt-level=s`, стабильная | 942 648 | 4 585 984 |
| `opt-level=3`, стабильная | 948 808 | - |
| `z` + `-Z build-std` + `optimize_for_size` + `immediate-abort` | **610 144** | **3 130 880** |
| `s` + `-Z build-std` + `optimize_for_size` + `immediate-abort` | 596 704 | 3 829 760 |

Решение: оставить `opt-level = "z"`. На Linux `s` дает на 13 КБ меньше, но на Windows
`z` меньше на 700 КБ, а Windows-библиотека в пять раз больше Linux-библиотеки, поэтому
один профиль на оба таргета - это `z`. Разница между `z` и `s` мала по сравнению с тем,
что дает сборка std из исходников: она снимает 37 процентов с Linux-библиотеки и 19 с
Windows-библиотеки.

Побочно измерено: сборка обоих таргетов с `-Z build-std` занимает около 1.5 минуты на
таргет; стабильная сборка с нуля в той же среде - 36 секунд; `nm -D` на Linux-библиотеке
показывает ровно пять точек входа платформы. Архив, который несет шаблон 1С, -
`build/dist/QrGeneratorNative.zip`, 1 714 395 Б (манифест и обе библиотеки).

## T002 - проверить, что платформа возвращает при отказе

Функция компоненты возвращает `Result<Vec<u8>, QrError>` и на ошибке отдает пустой
срез. Обертка (`ПроверитьИзображение`) принимает обе формы отказа - пустые двоичные
данные и `Неопределено` - потому что какая из них придет, зависит от платформы и **не
измерено**.

Что сделать: собрать тестовую сборку расширения и вызвать `СоздатьQRКод` с заведомо
неверными данными, посмотрев, что именно возвращает `ВнешняяКомпонента` - пустое
значение `ДвоичныеДанные` или `Неопределено`. Тогда лишнюю ветку в проверке можно
убрать.

## T003 - проверить кэш подключения в расширении конфигурации

Сделано: модуль `qr_QRCodeСерверПовтИсп` с `ReturnValuesReuse = DuringSession`, все
функции генерации подключаются через него, компонента подключается один раз за сеанс
вместо каждого вызова. Схема повторена по образцу конфигурации «Управление нашей фирмой»
(`docs/examples/ГенерацияШтрихкодаСерверПовтИсп.bsl`).

Не измерено: работает ли этот признак в **расширении** конфигурации так же, как в
конфигурации. Измерено только то, что общий модуль расширения не может хранить
переменные модуля, - отсюда и решение отдать кэш платформе.

Что сделать: `tests/bsl/run-tests.sh --build-only` (tier 1, без лицензии). Сборка
расширения платформой - единственная проверка, которая может упасть на непринятом
признаке. Факт кэширования из BSL не проверяется (нужен секундомер), поэтому в наборе
тестов есть только проверка, что модуль возвращает рабочую компоненту.

## T004 - набор тестов 1С не проходил

`tests/bsl` ни разу не выполнялся: на машине разработки нет ни `vrunner`, ни `ibcmd`,
ни лицензии 1С. Rust-часть проверена полностью (`cargo test --workspace`, 83 теста,
включая распознавание кода декодером `rqrr`), BSL-часть - нет.

Что сделать: `tests/bsl/run-tests.sh --build-only` для проверки сборки, затем
`--rebuild-base` с лицензией для прогона. Набор написан на YAxUnit; регистрация тестов -
через `ИсполняемыеСценарии`.

**Обновлено 2026-10-01: набор выполнен впервые.** Контейнер даёт `vrunner`, `ibcmd`,
платформу и лицензию — лицензия лежит в общем томе `onec-developer-license`, который
монтируется в `/var/1C/licenses`. На машине разработки всего этого не было, поэтому
BSL-часть не запускалась ни разу.

Первый прогон: **19 тестов — 15 успешно, 2 провалено, 2 ошибки.** Tier 1 проходит:
расширение и набор компилируются, архив компоненты лежит в шаблоне. Артефакты совпали
с измеренными в T001 — `QrGenerator_linux_x86_64.so` 610 144 Б,
`QrGenerator_win_x86_64.dll` 3 850 240 Б.

Все четыре падения — одна причина: `ВнешняяКомпонента` не подключается
(`Тип не определен (ВнешняяКомпонента)`), и из-за этого `КодВеренПроверяетЗапись` и
`ПустыеДанныеДаютИсключениеСТекстомПричины` тоже не проходят. Библиотека при этом
исправна: `ldd` показывает только `libc.so.6`, `dlopen` её загружает, в архиве есть и
манифест, и обе библиотеки под нужными именами. Значит вопрос не в сборке, а в
подключении компоненты на стороне платформы — это и есть предмет T004.

## T005 - nightly в контейнере разработки

`tools/native/build-addin.sh` требует nightly с компонентом `rust-src`: без них нет
`-Z build-std` и `optimize_for_size`, то есть всей экономии размера. `.devcontainer/devcontainer.json`
ставит только стабильный 1.92.0, поэтому в контейнере релизную сборку из коробки не
сделать; скрипт говорит об этом и подсказывает команду. То же самое в соседнем проекте.

Что сделать: либо добавить nightly и `rust-src` в образ (около гигабайта), либо собирать
релиз там, где nightly есть, и не делать вид, что контейнер это умеет. Выбор зависит от
того, где собирается релиз.

## T006 - ProcessPrng: библиотека не загружалась на Windows 7, 8 и 8.1

Симптом от потребителя: «Точка входа в процедуру ProcessPrng не найдена в библиотеке
динамической компоновки bcryptprimitives.dll». DLL не загружается вовсе - 1С не успевает
вызвать ни одну функцию.

Причина прочитана по таблице импорта (`objdump -p`): библиотека статически импортировала
`bcryptprimitives.dll!ProcessPrng`. Этот экспорт есть только с Windows 10; сам
`bcryptprimitives.dll` в Windows 7, 8 и 8.1 присутствует, а символа в нем нет. Импорт вносят
двое: std (его `ProcessPrng` без отката - откат на `RtlGenRandom` включается только при
`target_vendor = "win7"`) и `getrandom` 0.3. Убрать одну зависимость мало: std импортирует
символ сам, поэтому любая случайность в бинаре - `HashMap`, `getrandom` - тянет его в таблицу.

Решение: Windows-библиотека собирается под `x86_64-win7-windows-gnu`
(`tools/native/build-addin.sh`, `.cargo/config.toml`, `tools/native/pack-addin.sh`). Под этим
вендором и std, и `getrandom` берут `RtlGenRandom` (экспорт `ADVAPI32.dll!SystemFunction036`),
ABI не меняется, и одна библиотека обслуживает все x86_64 Windows. Цель tier 3, поэтому
`-Z build-std` из скрипта - не оптимизация, а условие сборки.

Проверено 2026-10-20 в контейнере (образ проекта, nightly и `rust-src` поставлены внутрь):
импорты win7-сборки - `ADVAPI32.dll SystemFunction036`, KERNEL32, msvcrt, ntdll, USERENV,
WS2_32; `bcryptprimitives.dll` в таблице нет, `api-ms-win-core-synch-l1-2-0.dll` тоже (этот
путь на win7 грузится через `LoadLibrary`). Экспортов ровно пять. Размеры: `.so` 610 088 Б,
`.dll` 3 131 904 Б, архив 3 743 122 Б. `cargo test --workspace` - 84 теста, все зелёные.

Не проверено: запуск в 1С на Windows 7 или 8.1 - такой машины нет. Проверка ограничена
таблицей импорта, а она и была причиной отказа загрузчика.
